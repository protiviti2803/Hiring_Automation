# Protiviti HR Portal: Database Structure Review

This document provides a comprehensive review of the SQLite database schema (`resume_analyzer.db`) used in the **Protiviti HR Resume Analyzer Portal**. It outlines each database table, its columns, data types, constraints, and relationship mappings.

---

## 1. Entity-Relationship Diagram (ERD)

The diagram below represents the logical relationships and foreign keys mapping the tables together.


## 2. Table Schemas & Breakdown

### Table 1: `client_demands`
Stores the original client request, the corresponding generated job description (JD), and extracted technical keywords.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique identifier for each demand entry. |
    | `demands` | `TEXT` | `NOT NULL` | The raw text input describing client requirements. |
    | `generated_JD` | `TEXT` | `NOT NULL` | The job description generated by the LLM. |
    | `keywords` | `TEXT` | `NOT NULL` | Serialized JSON list of key technical skills extracted. |
    | `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Timestamp indicating when the record was created. |

---

### Table 2: `interview_sessions`
Manages active recruitment cycles/sessions created per job role.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique session identifier. |
    | `role` | `TEXT` | None | Job title associated with this interview cycle. |
    | `total_candidates` | `INTEGER` | None | Total number of candidates assigned to this session. |
    | `completed_candidates`| `INTEGER` | None | Count of candidates who have finished interviews. |
    | `status` | `TEXT` | None | Session state (e.g., `"Active"`, `"Closed"`). |

---

### Table 3: `candidates`
Stores applicant profiles, parsed resumes, screening scores, and application status.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique applicant identifier. |
    | `session_id` | `INTEGER` | `FOREIGN KEY` (Logical) | Maps the candidate to their active `interview_sessions` card. |
    | `name` | `TEXT` | None | Candidate's name. |
    | `email` | `TEXT` | None | Candidate's email address. |
    | `resume_text` | `TEXT` | None | Parsed plain text contents extracted from the resume PDF. |
    | `status` | `TEXT` | None | Screen status (e.g. `"Accept"`, `"Reject"`, `"Pending"`). |
    | `resume_score` | `INTEGER` | None | Screening fit score generated during CV-JD matching. |
    | `reasoning` | `TEXT` | None | LLM evaluation comments explaining the score. |

---

### Table 4: `session_questions`
Maintains a log of interview questions standardized and asked during active candidate interviews.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique question log entry ID. |
    | `session_id` | `INTEGER` | `FOREIGN KEY` (Logical) | Session where this question was introduced. |
    | `candidate_id` | `INTEGER` | `FOREIGN KEY` (Logical) | Candidate who was asked this question. |
    | `raw_text` | `TEXT` | None | Original ungrammatical client notes logged by HR. |
    | `standardized_question` | `TEXT` | None | Standardized, grammatical question generated by the agent. |
    | `category` | `TEXT` | None | Classification (e.g., `"Technical"`, `"Domain"`, `"Scenario"`). |

---

### Table 5: `master_questions`
A global question bank storing unique standardized questions alongside their overall ask frequency, partitioned into Generic and Domain pools.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique master question ID. |
    | `question_text` | `TEXT` | `UNIQUE` | Unique, standardized interview question text. |
    | `frequency` | `INTEGER` | `DEFAULT 1` | Total number of times this question was asked across sessions (updates via UPSERT). |
    | `type` | `TEXT` | `CHECK(type IN ('GENERIC', 'DOMAIN'))` | Dynamic queue partitioning category. |

---

### Table 6: `client_feedbacks`
Persists post-interview client feedback, reasoning summary, and categorized out-of-the-box skills.
*   **Column Specifications:**
    | Column Name | Data Type | Constraints | Description |
    | :--- | :--- | :--- | :--- |
    | `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | Unique client feedback record ID. |
    | `original_demand` | `TEXT` | None | Contextual reference to original client requirement. |
    | `raw_feedback` | `TEXT` | `NOT NULL` | Raw notes typed in by the client post-interview. |
    | `candidate_name` | `TEXT` | `DEFAULT ''` | Name of the evaluated candidate. |
    | `role` | `TEXT` | `DEFAULT ''` | Target job title. |
    | `hard_skills` | `TEXT` | `DEFAULT '[]'` | Serialized JSON list of newly identified hard skills. |
    | `soft_skills` | `TEXT` | `DEFAULT '[]'` | Serialized JSON list of newly identified soft skills. |
    | `domain_knowledge` | `TEXT` | `DEFAULT '[]'` | Serialized JSON list of newly identified domains. |
    | `behavioral_knowledge`| `TEXT` | `DEFAULT '[]'` | Serialized JSON list of newly identified behaviors. |
    | `reasoning` | `TEXT` | None | Reasoning summary detailing the evaluation match. |
    | `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Timestamp indicating feedback creation date. |

## 3. Implementation Details & Storage Constraints

1.  **Logical Relationships (No Hard Cascades):**
    For flexibility and lightweight operations in SQLite, relational constraints (`session_id` and `candidate_id` mappings) are handled logically in application code (e.g. [db_service.py](file:///c:/Works/Hiring_Automation_Pipeline/HR_Automation_Pipeline/app/services/db_service.py)) rather than enforcing strict SQLite foreign key triggers that block deletions.
2.  **JSON String Arrays:**
    SQLite does not natively support array data types. Columns such as `keywords` in `client_demands`, or `hard_skills`, `soft_skills`, `domain_knowledge`, and `behavioral_knowledge` in `client_feedbacks` store values as serialized JSON string arrays (`"['Python', 'SQL']"`). They are parsed via `json.loads` and serialized via `json.dumps` at the service layer before read/write operations.
3.  **Dynamic Migrations:**
    The database initializes automatically on startup (`init_db()` in [database.py](file:///c:/Works/Hiring_Automation_Pipeline/HR_Automation_Pipeline/app/core/database.py)). In case the database file is copied or updated, startup-time schema checks dynamically inspect column tables using `PRAGMA table_info` and run `ALTER TABLE` operations to append new columns (such as `candidate_name` and `role`) to prevent runtime query crashes.
